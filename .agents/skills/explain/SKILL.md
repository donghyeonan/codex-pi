# Explain — 구현 기술 면접 해설

사용자가 구현 과제를 제출한 뒤 시니어 개발자의 기술 면접을 받는다고 가정한다. 목표는 요약이나 발표 대본이 아니라 **실제 구현의 동작과 한계를 이해하고, 근거 코드를 짚으며 꼬리 질문에 답할 수 있게 설명하는 것**이다. 별도 요청이 없으면 전반적인 구현을 다룬다. 일반 CS 면접 문제집이나 사용하지 않은 기술 설명으로 채우지 않는다.

## 질문은 제출물과 실제 작업에서 정한다

정해진 면접 질문 목록을 적용하지 않는다. 먼저 **과제 README·요구사항 → 사용자가 에이전트와 실제로 구현한 작업 → 제출용으로 작성한 설명**을 함께 읽고, 면접관이 그 자료를 보고 자연스럽게 물을 질문을 고른다. 제출 설명의 주장, 강조한 선택, 요구사항과 구현의 차이, 실제 작업에서 어려웠던 부분이 질문의 출발점이다.

- 질문마다 어느 README 항목·제출 설명 문장·구현 대목에서 나왔는지 드러낸다. 제출 설명이 없으면 만들어 내지 않는다. 위치를 찾을 수 없고 질문 선정에 중요하면 사용자에게 묻는다.
- '무엇을 만들었고 어떻게 동작하나요?'처럼 제출 내용을 설명하는 기본 질문부터 시작한다. 깊이는 해당 과제와 사용자의 설명에 맞춘다. 고급 동시성·확장성·보안 질문을 관례적으로 넣지 않는다.
- 코드와 제출 설명이 다르면 그 차이를 알려 주고 실제 구현 기준으로 설명한다. 사용자가 주장하지 않은 설계 의도나 성능 보장을 대신 만들어 주지 않는다.

## 먼저 실제 구현을 추적한다

- 과제 요구사항, 실행 진입점, 핵심 모듈, 데이터 모델, 외부 의존성, 설정, 테스트, `git diff`/`git log`, Problem Hub 티켓·시도·해결을 읽는다. 로컬 `problem-hub/` 또는 이미 연결된 중앙 Hub 중 현재 작업의 기록을 쓴다.
- 대표 사용자 동작을 입력부터 최종 출력까지 호출 관계와 실제 데이터 형태로 따라간다. 파일 이름 목록만 보고 동작을 추측하지 않는다.
- 정상 경로뿐 아니라 오류가 발생·변환·전파·포착되는 곳과 정리(cleanup)까지 추적한다. 구현하지 않은 처리를 있다고 설명하지 않는다.
- 코드로 확인한 동작, 직접 실행해 검증한 동작, 추정·미확인을 구별한다. 테스트 파일이 있다는 것과 테스트를 실행해 통과한 것은 다르다. 실행하지 않은 명령의 결과를 만들지 않는다.

## HTML의 설명 흐름

아래는 필요한 설명을 찾기 위한 참고 관점이지 고정 목차나 필수 질문이 아니다. 위 자료에서 고른 질문을 중심으로 HTML을 구성하고, 답을 이해하는 데 필요한 관점만 사용한다. 모든 항목을 채우려고 질문을 추가하지 않는다.

1. **무엇을 해결한 프로그램인가?** 요구사항과 완료 범위, 전체 구조, 실행 방법. 기초 용어와 각 경계가 필요한 이유부터 설명한다.
2. **이 데이터는 어디에서 어디로 흐르는가?** 대표 입력 하나를 끝까지 따라간다. 입력 → 검증 → 변환/비즈니스 로직 → 저장·외부 호출 → 응답·화면 순으로, 단계마다 실제 함수·파일과 입력/출력 예시를 보여 준다. 데이터의 소유자, 변경 시점, 상태 수명도 짚는다. 도식의 화살표가 실제 호출과 일치해야 한다.
3. **어떤 경우에 실패하며 어떻게 처리하는가?** 실제 경계별로 원인 → 감지 위치 → 처리/전파 → 사용자에게 보이는 결과 → 남는 상태와 정리를 설명한다. 입력 오류, 없는 데이터, 외부 의존성 실패, 중복·동시 요청, 취소 등 구현에 관련된 경우만 다룬다. 재시도·타임아웃·롤백·멱등성은 있는 것과 없는 것을 분명히 한다. 처리하지 않은 경우 실제로 어떻게 깨지는지도 설명한다.
4. **왜 이렇게 설계했는가?** 모듈 경계, 데이터 구조·스키마, 상태 관리, API와 라이브러리 선택을 과제 제약과 연결한다. 대안과 비용을 비교하되, 기록에 없는 이유는 '코드에서 추정한 이유'로 표시한다. 현재 구현과 개선 제안을 섞지 않는다.
5. **규모나 요구사항이 바뀌면?** 관련된 성능·복잡도, I/O, 동시성, 보안/권한, 유지보수 한계와 변경 지점을 짚는다. 예: 입력이 10배면 어느 부분이 먼저 병목인가, 저장소를 바꾸면 어느 파일이 바뀌는가. 측정하지 않은 성능 수치는 만들지 않는다.
6. **맞게 동작한다는 근거는?** 중요한 요구사항·실패 경로와 테스트를 연결한다. 검증 명령과 실제 결과, 미검증 영역, 알려진 결함을 구분한다.

## 면접 질문과 연결하는 방식

각 핵심 장은 **제출물에서 질문이 나온 배경 → 예상 질문 → 짧은 답변 → 필요한 코드와 원리 설명**으로 구성한다. 꼬리 질문은 그 답변에서 자연스럽게 이어질 때만 덧붙인다. 면접 답변만 나열하지 말고 왜 그렇게 답할 수 있는지 가르친다.

- 예: 제출 설명에 '검색 결과를 캐싱했다'고 썼다면 → “무엇을 캐싱하며 왜 넣었나요?” → 실제 저장·조회 코드와 선택 이유 → 필요할 때만 “원본이 바뀌면 결과는 어떻게 되나요?”로 이어간다. 캐싱을 쓰지 않은 과제에는 이 질문을 넣지 않는다.
- 핵심 코드 발췌는 `파일:줄`과 함수 이름을 붙이고 원문을 유지한다. 생략은 표시하고, HTML 특수문자를 escape한다. 긴 코드 전체를 던지거나 중요한 분기를 숨기지 않는다.
- 용어는 처음 등장할 때 이 코드에서의 의미를 풀고, 구체적인 데이터 예시로 설명한다.
- 마지막에 사용자가 혼자 답해 볼 핵심 질문과 '코드에서 확인할 위치/답에 꼭 들어갈 내용'을 `<details>`로 제공한다. 질문 개수를 채우지 말고 구현의 주요 경계를 커버한다.
- AI가 작성한 것을 사용자가 직접 설계·검증했다고 말하는 면접 답변을 만들지 않는다. 설계 기록과 실제 기여가 확인되는 범위에서 설명한다.

## 산출물

- [assets/template.html](assets/template.html)의 스타일을 활용해 `.codex-pi/explain/index.html` **하나만** 만든다. Markdown 복제본은 만들지 않는다. 기존 사용자 파일은 함부로 삭제하지 않는다.
- 한국어로 기초부터 설명한다. `.src`는 근거 코드, `.narration`은 옆에서 설명해 주듯 읽히는 해설이다. 목차와 장별 앵커, 필요한 inline SVG 데이터 흐름도를 사용한다. 외부 CDN 없이 파일만 열어 읽을 수 있게 한다.
- 생성 후 링크·앵커·코드 인용·HTML escape와 모바일 가독성을 확인한다. 브라우저 검증을 못 했다면 그 사실을 밝힌다. 코드의 미확인 동작을 HTML 완성으로 검증했다고 주장하지 않는다.
- 사용자에게 저장 경로를 안내한다. 서버가 필요할 때만 `python3 -m http.server 8765 --bind 127.0.0.1 -d .codex-pi/explain`을 사용한다.
